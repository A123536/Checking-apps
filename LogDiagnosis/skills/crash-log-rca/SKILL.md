# 宕机日志根因定位（轨交信号系统）

核心循环：**定终局 → 切周期 → 逐层下钻 → 每层回代码定位 → 钻到原始值 → 给出证据边界**。

你不是在“读日志”，你是在**沿一条调用链反向追溯**：从系统主动宕机的那一刻，一层一层往回找，直到找到那个“最一开始出错的动作”。

## 一、先建立心智模型（跳过这步必然误判）

### 1.1 日志归属藏在文件名里

`DownLog_<板卡>_<端><系><网>_<时间>.csv`，例如 `DownLog_OPB_H_A_G_2026.11.04_11.13.02.txt宕机.csv`

| 维度 | 取值 |
|---|---|
| 端 | H 头端 / T 尾端 |
| 系 | A 系 / B 系 |
| 网 | G 绿网 / P 紫网 |
| 板卡 | ATP 主机 / IPB 输入 / OPB 输出 / SPB 信号 |

一端插箱 = 4 种板卡 × A/B 双系；一套设备 = 头尾两端。**同板另一系（A↔B）是最强的对照组。**

### 1.2 软件结构

**上电阶段**：初始化 → 上电自检 → 上电信息二取比较 → 上电主备表决

**周期运行阶段**：
- 主正常运行 / 备正常运行
- 跟随态（跟随升备业务逻辑）
- 系统异常状态

主/备正常运行时，一个周期固定跑 6 个时间片：

| 时间片 | 工序顺序 | 日志边界编码 |
|---|---|---|
| 输入 | 自检 → 时间戳信息二取比较 → 输入接收 → 输入二取 → 输入同步 → 输入处理 | `0x0a4b` 开始 / `0x0a4c` 结束 / `0x0064` 时间片检查 |
| 应用 | 自检 → 业务逻辑处理 | `0x0a61` / `0x0a62` / `0x0068` |
| 输出 | 自检 → 输出数据处理 → 输出二取表决 | `0x0a64` / `0x0a65` / `0x006f` |
| 主备 | 自检 → 系间通信表决 | `0x0a67` / `0x0a68` |
| 发送 | 自检 → 发送信息二取比较 → 发送数据 | `0x0a6a` / `0x0a6b` / `0x0089` |
| 空闲 | 自检 → 空闲阶段业务处理 | `0x0a8b` / `0x003f` |

### 1.3 三条决定性的系统性质

1. **代码是一个超级大的死循环**，周期往复执行。日志不是“事件流”，是“周期的重复快照”。
2. **看门狗超时不会自然发生，是系统主动触发的。** 这是故障安全的最后一环：判据不过 → 进异常态 → 主动去死。**看到 `0x0091` 不要判“卡死/死锁”**，那是普通系统的经验，在这里方向完全相反。
3. **每个微周期开头都有自检**，自检是系统内置的探针。自检结果本身就是一个定位锚点。

### 1.4 数据格式的两个实测坑

- **表头是错位的**：名义上 7 列，实际只有 5 列 —— `级别, 编码, 描述, 原始值, 解析值`。第一列是级别（提示/警告/错误/调试），不是板卡类型。
- **描述可能为空、也可能含逗号或断引号**（如 `0x051f`、`0x0aa1` 无描述；`0x0e40` 那行有孤立引号）。解析时按“前两列 + 最后一列固定”切更稳；**描述缺失时，一切以编码回代码为准**。

## 二、四条铁律

1. **倒序读。** 从文件末尾往上，先看“最后发生了什么”，再问“它是被谁触发的”。
2. **编码必须回代码定位。** 日志文本只给现象，代码位置给性质。同一个“失败”，打印在异常分支里和打印在返回值检查里，含义完全不同。查不到代码就不许下语义判断。
3. **一次只钻一层。** 每层只回答一句话：“上一层这个结果，是哪一步产生的？”不要跳层，不要平行罗列可能性。
4. **结论必须带证据，到边界必须停。** 每条判断都要能指到具体行；钻不下去就明说缺什么数据，不许硬猜。

## 三、第一步：用周期号切段（唯一可靠的时间基准）

`0x0a1a`（新周期号）**每个周期只打印一次**。它的语义不是“时间戳”，是**完成凭证**：

> 只要 `0x0a1a` 打出来了，就一定表示**上一个周期已完整执行且无异常**。

于是切段规则极硬：

1. 从文件末尾往上，找**最后一个** `0x0a1a`。
2. 它之后的全部行 = **唯一一个没跑完的周期** = 出事的那一圈。
3. 该段内**第一处失败判据** = 故障起点（注意：不是第一处“错误”级日志）。
4. 段内应出现却没出现的微周期，本身就是证据（例如只走到输入就没下文了 → 卡死在输入）。
5. **反向利用**：`0x0a1a` 之后若又有新的 `0x0a1a`，说明那个周期整体是好的，可以直接排除。

补充事实：
- 每个周期开头有一组**固定的周期级自检块**（约 19 行：时钟互检、电源、寄存器、CPU、继电器、24V、插箱号、板卡 ID、板卡类型、输入控制流自检等）。**逐行对照上一周期，是最快的体检。**
- 文件里通常能看到 **2 个周期**：一个完整的健康周期 + 一个断掉的故障周期。**这天然构成对照组，一定要用。**
- `0x0a1a` 可能在本文件出现两次，**取故障前最后一次**。
- 别把 `0x0ab8`（主机板周期号）当成自己的周期号 —— 那是另一个板子的计数，数值不同源。

## 四、五层判据模型（下钻地图）

故障的呈现是分层的。**从上往下钻，每层只认“上一层是谁产生的”。**

| 层 | 作用 | 典型编码 | 能回答 | 常见错误 |
|---|---|---|---|---|
| 5 终局 | 主动宕机最后动作 | `0x0091` 看门狗超时 | 什么时候死 | 判成“卡死/死锁” |
| 4 保护 | 保护判据触发 | `0x008c` 平台状态异常宕机、`0x0033` 本系状态 | 触发了哪条保护 | 当成根因 |
| 3 聚合 | 阶段/功能/自检整体 | `0x0063`/`0x0088` 阶段执行结果、`0x0084` 自检结果、`0x0054` 功能执行结果 | 故障域在哪个微周期、哪项功能 | 停在这里就说“二取失败了” |
| 2 判据 | 具体功能判定 | `0x0051` 比较超时、`0x00cd` 接收状态、`0x0052` 接收处理、`0x0053` 表决结果 | 哪一步没过 | 不知道“为什么没过” |
| 1 原始值 | 物理/数据事实 | `0x0a75` 驱动返回值、`0x0f07` 连续出错周期数、`0x0ac0`/`0x0ac1` 双方长度、`0x0f05` 时间戳 | 第几路、差多久、少多少 | 根本没往下看 |

**规则：至少钻到第 2 层才能给结论；能钻到第 1 层的，必须钻到第 1 层。**

## 五、下钻规程（每一层都问这四个问题）

拿到一条可疑日志，依次问：

1. **它打印在哪个函数里？**（回代码，按编码常量检索）
2. **这个函数属于哪个微周期的哪道工序？**
3. **它判失败后走哪条分支？**（继续走？跳过？置异常态？触发宕机？）—— 这决定它是“结果”还是“原因”。
4. **它内部还有没有更细的打印？**（往下一层）

三个判断“这是原因还是结果”的经验：
- 打印在**异常处理/保护动作**里的 → 结果。
- 打印在**功能返回值检查**里的 → 中间层。
- 打印在**原始数据/硬件接口返回值**里的 → 最接近原因。

### 下钻有两种形态，不能混用

| 形态 | 适用 | 做法 | 什么时候停 |
|---|---|---|---|
| **链式** | 二取、通信、功能调用 | 沿调用链一条道往下找断点 | 找到第一处断点即停 |
| **扫面式** | 自检（上电自检、各微周期自检） | 日志一次性给出了**全部自检项的返回值**，必须逐项核对 | **必须穷举完，列全所有异常项** |

**把扫面式当链式做，是自检类漏判的主要来源。**

## 六、专项 A：二取类问题

二取（双 CPU 比对）失败的固定套路：

1. **功能级结果**：`0x0054`（输入二取功能执行结果）= 失败 → 确认二取这一步没过。
2. **是否收到对端数据**：`0x00cd`（二取交互接收状态）。正常为 `0x55/85`，`0xaa/170` 表示**没收到**。
3. **双方数据长度**：`0x0ac0`（本 CPU 长度）vs `0x0ac1`（另一 CPU 长度）。长度不等 → 数据不完整；对端为 0 → 对端压根没发。
4. **时间戳比对**：`0x0f05`（本机时间戳）、`0x0051`（时间戳二取比较结果）。`0x59` = **比较超时**，说明对端数据没按时到达。
5. **锁定周期号**：`0x0a1a` 取故障前最后一次。

**定责框架**（最终定责通常需要另一系的日志，见第九节）：

| 现象组合 | 指向 |
|---|---|
| 本机比较超时 + 对端长度为 0 + 接收状态失败 | 对端没发 → 对端 CPU 未正常运行 |
| 本机比较超时 + 对端长度正常 + 接收状态正常 | 数据到了但晚了 → 链路/调度延迟 |
| 接收状态失败 + 长度正常 | 数据到了但校验不过 → 数据合法性/同步问题 |

注意层级：**“二取功能失败”是触发链的第一环，不是根因**；“没收到数据”才是原因的最内层；“比较超时”是时间上最早的信号。三者要分开写，不能混成一句“二取失败导致宕机”。

## 七、专项 B：自检类问题

**自检类是扫面式，不是链式。** 不管是上电自检还是某个微周期的自检，日志里**把所有自检项的返回值都记录下来了**。所以一旦判定为“自检异常”，第一件事不是找“第一个不对劲的”，而是**把这些自检项一个一个全部核对一遍**。

### 第一步：穷举（这一步做不完，后面的结论都不可靠）

1. 把该阶段日志里出现的**每一个自检项**列出来（上电阶段的全套 / 输入 / 应用 / 输出 / 主备 / 发送 / 空闲，各自的自检项集合不同）。
2. 对每一项**回代码**确认两件事：**正常返回范围**是什么、**判定条件**是什么。
3. 标出所有不正常的项。

**注意：不能凭“0x55 就是成功”一概而论。** 正常值可能是 0、可能是非 0、可能是某个枚举，逐项以代码为准。

**可能只有一项异常，也可能多项同时异常。** 多项时不要擅自认定“只有第一项是真因”，也不要认定“都是真因”。

### 第二步：区分致宕项和伴生异常

不是所有异常项都会导致宕机。回到代码看这一项失败后的分支：

| 类型 | 代码里的表现 | 写进结论的方式 |
|---|---|---|
| **致宕项** | 失败即返回失败，层层上抛 → 触发异常态 → 看门狗 | 作为根因候选，往下钻到原始值 |
| **伴生异常** | 只记录、不中断，或与宕机无因果关系 | 单独列出，注明“同时存在，非致宕” |

两者必须分开写。把伴生异常当根因，会给出错误的整改方向。

### 第三步：对每个致宕项往下钻到原始值

1. **驱动接口返回值**：如 `0x0a75`（12 路安全开关量输出继电器反馈）。**正常为 0，非 0 即异常**（`0x00 0x00 0xff 0x00` = 65280）。
2. **连续出错周期数**：如 `0x0f07`，32 字节数组，**字节下标 = 通道号**。
3. **通道定位**：计数器数组与位掩码互相对照。例：`0x0f07` 第 8–15 字节为 3，而 `0x0a75` 的 `0x0000FF00` 恰好第 8–15 位置 1 —— 两个打印指向同一批通道，才能确证。
4. **阈值语义**：代码对每路设阈值（实测为 2），**计数器 > 阈值才判失败**。所以计数器 = 2 时自检仍通过，涨到 3 才宕机。这是**去抖设计**：容忍单周期抖动，连续异常才判死。
5. **反推起点**：计数器 = N 说明故障已持续 N 个周期。**若日志只覆盖 2 个周期而计数器已是 2 或 3，说明真正的起点在日志开始之前** —— 这是日志不够长时的定位手段。

### 第四步：交出自检项核对表

自检类的结论必须附这张表，**一行都不能省**（正常项也列，用来证明你确实穷举过）：

```markdown
| 自检项 | 编码 | 本周期返回值 | 代码里的正常范围 | 判定 | 是否致宕 |
|---|---|---|---|---|---|
```

自检类的关键认知：**自检是“迟发型”报警，不是第一现场。** 原始返回值往往在自检失败之前就已经异常了，自检只是“攒够了才发作”。所以要在更早的周期里找同一个原始值的变化。

## 八、三种对照（把“猜”变成“证”）

1. **跨周期对照**（同一文件内）：同一编码在健康周期与故障周期的值。例：`0x0051` 一个“成功”一个“比较超时”；`0x0f07` 一个 2 一个 3。**这是最硬的证据，几乎不花钱。**
2. **跨系/跨端对照**（需要另一份文件）：A 系 vs B 系、头端 vs 尾端。同板另一系是二取问题的必查项。
3. **双视图对照**（同一事实的两种打印）：位掩码 vs 计数器数组；声明长度 vs 实际长度；本机时间戳 vs 对端时间戳。**两个视图对得上，结论才成立。**

## 九、走到证据边界就停

单份日志的证据是有上限的。典型边界：

- **二取类**：能确认“没收到对端数据”，但**分不清是硬件链路坏了还是对端 CPU 早崩了**。
- **自检类**：能确认“第 X 路反馈异常、已持续 N 周期”，但**分不清是继电器本体、驱动电路还是回采回路**。

到边界时，输出三句话，不要越界猜：

1. **已确认到哪一层**（列证据）。
2. **下一层需要什么**（通常是：同板另一系的日志 `H_B_*` / 对端日志 / 硬件回路测量）。
3. **在该数据到位前，哪些结论不能下**。

## 十、输出格式

```markdown
## 结论
- **根因**：一句话，到工序/通道/配置项
- **触发链**：根因 → 判据失败 → 阶段失败 → 保护动作 → 看门狗超时
- **置信度**：高/中/低 + 依据

## 周期切段
| 周期号 | 状态 | 依据 |
（说明哪个周期是完整的、哪个断在哪一步）

## 下钻路径
| 层 | 编码 | 原文 | 回代码得到的性质 | 得出什么 |

## 证据
| # | 行号 | 编码 | 原文摘录 | 支撑哪一跳 | 等级（直接/间接/推断） |

## 对照
| 维度 | 健康侧 | 故障侧 | 差异说明 |

## 自检项核对表（自检类必填，正常项也要列）
| 自检项 | 编码 | 本周期返回值 | 正常范围 | 判定 | 是否致宕 |

## 排除项
| 曾怀疑 | 排除依据 |

## 处置
- **止血**：
- **根治**：
- **验证**：修复后日志里应看到什么

## 证据边界
- 已确认到：
- 还需的日志/数据：
- 在此之前不能下的结论：
```

## 十一、交卷自检

逐条确认，任何一条不过就回去补：

1. 我是否先用 `0x0a1a` 切了段，而不是从第一行读起？
2. 我是否确认了这个周期**没跑完**（缺哪个微周期）？
3. 我是否钻到了第 2 层以下？能到第 1 层吗？
4. 每个编码我都回代码确认过它打印在哪个函数吗？
5. 我是否做了跨周期对照？
6. 我是否把“触发链第一环”和“原因最内层”分开了？
7. **若是自检类：我是否把该阶段所有自检项都列出来了（含正常项）？有没有漏掉第二个、第三个异常项？**
8. **若是自检类：我是否区分了“致宕项”和“伴生异常”？**
9. 我是否说明了证据边界，而不是把推测写成结论？
10. 拿这份报告去改代码的人，知道改哪里、怎么验证吗？

## 十二、明确禁止

- 把 `0x0091` 看门狗超时解释成“系统卡死/死锁”。
- 把第一条“错误”级日志当根因（健康周期里也会有错误）。
- 用 `0x55=成功`、`0xaa=失败` 的模式做全局推断（`0x0091` 的 `0x55` 就是“失败”）。
- 靠行号先后判断因果（同微周期内日志顺序不等于执行顺序）。
- 停在“XX 失败”这一层就交卷。
- **自检类只核对第一个异常项就收工**（漏判多异常的主因）。
- **不区分致宕项与伴生异常**，把同时存在的异常一起当根因。
- 把“可能是 A、B、C”列一堆而不做取舍。
